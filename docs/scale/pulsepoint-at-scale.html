▸ What actually changed

One change reframes the entire problem.

Round one collected feedback — a human clicks "submit bug" a few times a day. That is human-paced traffic: slow, bursty, forgiving. Round two adds analytics events — every page view and click, fired automatically by a snippet with no human present. That is machine-paced traffic, and the numbers are a different kind of problem, not a bigger version of the old one.

🪣 The analogy: round one was a suggestion box in a shop — someone drops a card in now and then. Round two is a stadium turnstile counter during a match. Same idea (counting things), completely different engineering. You don't build a turnstile the way you build a suggestion box.

The single most important fact in this whole document: load is not evenly spread. A power law rules — the top 0.5% of tenants generate ~80% of events, and one tenant (the "whale") does ~15,000/sec by itself. Every design decision below flows from confronting that.

1 Placement & sharding

How do 40,000 tenants spread across infrastructure — and what happens when one tenant is bigger than a node?

The naïve answer is hash(tenant_id) % N: hash the tenant and mod by the number of shards. It spreads tenants evenly — but it dumps the whale entirely onto one shard, and that shard melts. Press the button and watch.

Two strategies, same whale. Hash sends it all to one shard. A directory lets us put the whale on its own dedicated shard.

The design

  • Shard key: tenant_id — keeps all of one tenant's data co-located, so every query and every rollup stays on a single shard (no cross-shard joins).
  • Placement is a lookup, not a formula. A small tenant directory maps tenant_id → (region, shard, tier). Because it's a lookup, we can move a tenant by editing one row — impossible with a hard-coded hash.
  • The whale gets its own shard. When a tenant exceeds a pooled shard's capacity, the directory points it at a dedicated node. Skew is handled by placement, not by pretending load is uniform.
  • Geo first. Region is the outer key (EU tenants → EU shards) for latency and data residency; the directory picks a shard within the region.
💡 Your idea: "geo-shard by region A/B/C/D, then follow-the-sun to save cost." Adopted as the outer layer — it answers the EU-residency live question for free. The gap you didn't see: region spreads tenants, but the whale lives in one region, so you still need the directory to split it onto its own box inside that region. Geography is the first cut, not the whole answer.

4 Hot-tenant live migration

The centerpiece. Move the whale to its own database with zero downtime and zero lost/double-counted events.

Detection comes first: the per-tenant metrics (next section) flag a tenant whose rate or storage crosses a threshold. Then the cutover runs as a sequence where every step is reversible. Press play.

1
Dual-write

Start writing every new event to both old and new shard. No reads switch yet.

2
Backfill

Copy historical events to the new shard in the background while dual-write keeps it current.

3
Verify counts

Compare event counts & rollup totals old vs new. They must match exactly before proceeding.

4
Cutover reads

Flip the directory entry → reads now hit the new shard. Keep dual-writing a little longer.

5
Decommission

Stop writing to the old shard, reclaim its space. Migration complete.

Reads only move after counts match. If anything looks wrong before step 4, flip the directory back — the old shard never stopped receiving writes, so rollback is instant and lossless.
⚠️ Why billing stays exact: dual-write means no event is lost during the move. The verify step means we never cut over to a shard that's missing data. And because the old shard stays live until step 5, rollback at any point before cutover loses nothing. That rollback plan is what separates a real migration from a hand-wave.

5 Ingestion correctness (idempotency)

The endpoint is public, clients retry, and usage drives billing — so you cannot over- or under-count.

Today's code (feedback.ts) generates the event ID server-side with randomUUID(), so a retried request becomes a second row — a double-count and a wrong invoice. The fix: the client sends a unique idempotency key per event; the server counts each key once. Send the same event three times (a retry storm) and watch each counter.

Same event, sent three times. Without a key: counted 3× → wrong bill. With a key: counted once → exact.
💡 You named this one yourself: "like not getting double-charged when you buy something online." Exactly right — that's textbook idempotency, the same mechanism Stripe uses (an Idempotency-Key header). Effectively-once aggregation: dedupe on the key, and late/out-of-order retries become harmless. This is the spike we'll build.

Handling late & out-of-order events

Events carry a client timestamp, so an event that arrives 5 minutes late still lands in the correct time bucket. Rollups for a window stay "open" briefly to absorb stragglers, then seal. A nightly reconciliation job recomputes counts from raw and compares against what was billed — if they ever drift, we catch it before the invoice, not after.

💡 Your caching idea, re-pointed: you suggested caching user info on login. Low value — people log in once a day. 7 Zero-downtime schema evolution

Add a field to the event model across 40,000 tenants with no maintenance window.

Round one needed a maintenance window because one shared ALTER TABLE locks the table every tenant depends on. The fix is the expand → migrate → contract pattern, and it behaves differently per isolation model:

ModelAdding a fieldTrade-off
Shared tableOne ADD COLUMN (nullable, no default) is instant in modern Postgres; backfill in batches.One change for all — but one mistake hits everyone.
Schema-per-tenantRoll the change tenant-by-tenant; pause/resume safely.Isolated blast radius, but 40k migrations to orchestrate.
DB-per-tenantDeploy per database, region by region.Total isolation; slowest to roll out everywhere.
🔁 Expand → migrate → contract: (1) expand — add the new field as optional, deploy code that writes both old and new; (2) migrate — backfill existing rows in small batches; (3) contract — once everything uses the new field, drop the old one. At no point is the table locked or the app down. Same discipline as the live migration: every step is reversible.

8 Per-tenant observability & cost

When the system is slow or expensive, which tenant caused it? And is a Free tenant losing us money?

Every log line, metric, and trace is tagged with tenant_id. That single discipline lets you answer "who made us slow?" instantly (it's how migration detection finds the whale) and "what does each tenant cost?" by attributing writes, storage, and compute back to the tenant that caused them.

📉 Live-question preview — "Free tenants are collectively unprofitable." Levers the cost model hands you: (1) tighten Free quotas / shorten Free retention (cheap, mild churn); (2) raise the rollup ratio so Free tenants cost near-zero to store; (3) pack more Free tenants per shard (cheaper per tenant, higher blast radius); (4) push heavy Free tenants toward Pro. Each lever trades cost against experience — and you can only reason about them because everything is tagged by tenant.

⚠ What breaks next (at 10×)

The clearest seniority signal: name the next bottleneck and roughly when you hit it.

1. The tenant directory

At 400k tenants, the placement lookup itself becomes hot and a single point of failure. Fix is incremental: replicate it, cache it at every ingest node. Hit it around 5–10× tenant count.

2. A super-whale > one node

Today's whale fits one dedicated box. At 10× it won't — now you must shard within one tenant (by event-type or time). This is a partial rewrite of the placement assumption "one tenant = one shard." The real cliff.

3. Rollup write amplification

At 2.5M events/sec, even rollup updates contend. Fix is incremental: pre-aggregate in the stream (batch in memory before the DB) so the database sees thousands of updates/sec, not millions.

4. Cross-region the dashboard

A global Enterprise wants one dashboard over EU+US data that can't be moved. Needs cross-region rollup federation — query each region, merge. New subsystem, not a tweak.

🎯 The honest summary: three of the four next bottlenecks are incremental (replicate, cache, batch). The one that's a partial rewrite is the super-whale — the day one tenant exceeds one node, "one tenant = one shard" breaks and you shard inside a tenant. Knowing which fixes are incremental vs. structural is the whole point of this section.

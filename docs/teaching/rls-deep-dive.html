PulsePoint — How RLS Makes Leaks Impossible

Stage 2a architecture · Part 3 of ~5 · The crown jewel — try to break it at the bottom

A · Three roles, each with the least power it needs

A database role is a login with its own permissions. We use three, so no single connection is all-powerful. This is the principle of least privilege.

pulsepoint_migrate

  • OWNS the tables; creates/changes schema + RLS policies
  • Used only at setup/deploy
  • The running app NEVER connects as this

pulsepoint_app

  • Read / insert / update — but only within one tenant
  • Powers the dashboard (read path)
  • Not an owner → fully subject to RLS

pulsepoint_ingest

  • INSERT feedback only
  • Powers the public widget (write path)
  • No SELECT grant at all → literally cannot read anyone's data

B · The trap most people fall into

RLS does NOT apply to the table's owner, and never to a superuser. If the running app happened to own its tables, every policy would be silently skipped and "isolation" would be fake.

We avoid it two ways, belt-and-suspenders:

  • Ownership: tables are owned by pulsepoint_migrate — a role the app never logs in as. The runtime roles (app, ingest) are non-owners, so RLS always applies to them.
  • FORCE: we also add ALTER TABLE … FORCE ROW LEVEL SECURITY, which makes policies apply even to the owner. So even a future mistake can't bypass it.

C · The policy has two halves: a read gate and a write gate

Every RLS policy can have a USING clause and a WITH CHECK clause. You need both — one guards reading, the other guards writing.

USING — the read gate

Controls which EXISTING rows you can SELECT, UPDATE, or DELETE.

"You may only see / touch rows where tenant_id = me." Other tenants' rows are simply invisible — a query for them returns nothing.

WITH CHECK — the write gate

Controls which rows you're allowed to INSERT (or the new version on UPDATE).

"Any row you write MUST have tenant_id = me." Without this, you could insert a row stamped with someone else's tenant. This is the half people forget.

Here's the actual policy for the dashboard role on feedback:

-- turn RLS on, and force it even for the owner
ALTER TABLE feedback ENABLE ROW LEVEL SECURITY;
ALTER TABLE feedback FORCE  ROW LEVEL SECURITY;

-- the dashboard role: can only see/write its own tenant's rows
CREATE POLICY tenant_isolation ON feedback
  FOR ALL TO pulsepoint_app
  USING      (tenant_id = current_setting('app.current_tenant_id')::uuid)
  WITH CHECK (tenant_id = current_setting('app.current_tenant_id')::uuid);

-- the public role: insert-only, locked to the key's tenant
CREATE POLICY ingest_insert ON feedback
  FOR INSERT TO pulsepoint_ingest
  WITH CHECK (tenant_id = current_setting('app.ingest_tenant_id')::uuid);
💡 current_setting('app.current_tenant_id') reads a per-request variable. The policy says "the row's tenant must equal whoever this request is." The database enforces it on every query automatically — the app can't forget.

D · How the tenant gets set — safely — on every request

Where does app.current_tenant_id come from? The app sets it at the start of each request, inside a transaction.

BEGIN;                                              -- start a transaction
SET LOCAL app.current_tenant_id = '…alpha-uuid…';   -- from the SESSION, never a URL param
SELECT * FROM feedback;                          -- RLS auto-filters to Alpha
COMMIT;                                             -- SET LOCAL resets here
💡 Why SET LOCAL + a transaction? Apps reuse database connections (a "pool") for speed. SET LOCAL ties the tenant value to this one transaction — it auto-clears at COMMIT, so it can never leak into the next request that reuses the same connection. Plain SET would stick around and leak. This detail is the difference between safe and catastrophic.
Fail closed: if the app ever forgets to set the variable, current_setting(...) matches nothing, so you see zero rows — not everything. A bug makes the app show too little, never too much. Safe by default.

E · The whole defense, stacked (defense in depth)

No single trick — layers. An attacker has to beat all of them.

  1. Unguessable ids — UUIDs, so other tenants' records can't be enumerated.
  2. Tenant from the session — never trusted from a URL or request body.
  3. USING gate — can't read another tenant's rows (they're invisible → 404).
  4. WITH CHECK gate — can't write a row tagged as another tenant.
  5. Role grants — the public role can't read anything; the app role isn't an owner.
  6. FORCE RLS — applies even to the owner, so future mistakes can't bypass it.
  7. Fail closed — forget the tenant, and you get nothing.

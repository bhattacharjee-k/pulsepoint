💡 The widget is vanilla JavaScript (no big framework → tiny + fast) and lives in a Shadow DOM bubble so the host page's CSS can't break it and its CSS can't leak out. On load it reads the public key from its <script> tag, fetches that tenant's config, and themes itself. States it handles: idle → open → submitting → thanks → error.

D · The 30-second demo (what a reviewer does)

  1. docker compose up — boots the app + Postgres + runs the seed (2 tenants, 3 users, sample feedback).
  2. Open demo-alpha.html → blue widget → submit a bug.
  3. Open demo-delta.html → amber widget → submit a feature.
  4. Log in as admin@alpha.com → see only Alpha's feedback, including the one you just sent; stats tick up.
  5. Log in as admin@delta.com → see only Delta's. The wall is visible in 5 seconds.
  6. (Bonus) log in as Casey (member) → can triage, but Settings is gone.

E · What happens at scale (bursty traffic + noisy neighbor)

The challenge asks: a tenant goes viral (or a bot finds the endpoint) — thousands of submissions a second. How do you keep ingestion from taking down the dashboard?

💡 Two things are real even in v1, not just talk: (1) the ingest and dashboard paths use separate connection pools, so a write flood can't starve reads; (2) rate limits per key + per IP contain a noisy neighbor. The queue and read-replicas are the honestly-labeled "with more time" upgrades.

PulsePoint — Two APIs, Two Threat Models

Stage 2a architecture · Part 4 of ~5 · Why the public door and the staff door are built differently

A · Two surfaces, deliberately different shapes

The whole point: a door open to the entire internet and a door only staff use should NOT be built the same way.

🌐 Public Ingest API

Who calls it
The widget, from anyone's website
Auth
X-Tenant-Key: pk_… (routes to a tenant; not secret)
Can do
Submit feedback (insert-only) · read its own widget config
Main threats
Spam floods · junk/oversized payloads · stored XSS · forged tenant
Key defenses
Rate limit (per key + per IP) · strict validation · tenant from key only · insert-only DB role

🔐 Admin API

Who calls it
The dashboard, used by logged-in staff
Auth
Session cookie (logged in with email + password)
Can do
List / filter / search feedback · update status · notes · assign · settings
Main threats
Session theft · CSRF · IDOR · privilege escalation (member→admin)
Key defenses
HttpOnly+SameSite cookie · tenant from session · RLS backstop · app-layer role checks

B · Auth choice — why session cookies (not JWT)

Both are industry-standard. For a single same-origin dashboard, a server-side session is the simpler, safer fit.

Session cookie (our pick)JWT token
How it worksServer stores the session; browser holds a cookie pointing to itServer hands the browser a signed token it carries around
Log someone out?Easy — delete the sessionHard — token is valid until it expires
XSS exposureCookie can be HttpOnly (JS can't read it)Often stored where JS (and XSS) can read it
Best whenOne app, same origin (us)Many services / different origins / huge scale

The cookie carries these flags, and each one closes a specific hole:

HttpOnly — JavaScript can't read the cookie, so a stored-XSS script can't steal the session.
SameSite=Lax — other sites can't quietly use your cookie → blocks most CSRF.
Secure — only sent over HTTPS (in production).
💡 The honest downside (worth saying out loud): sessions need a server-side store and don't "free-scale" across many servers the way stateless JWTs do. For this product that trade is clearly worth it — and naming the downside is exactly the senior signal the challenge rewards.

C · The CORS myth — the #1 thing people get wrong

CORS is NOT a security guard. It's a browser rule about whether one website's JavaScript may read the response from another website. It does nothing to stop a bot, curl, or a script from sending a request.

🌐 Public ingest → CORS wide open

The widget lives on Alpha's and Delta's sites (different origins), so the endpoint must accept calls from anywhere: Access-Control-Allow-Origin: *, and no cookies. CORS being open here is fine — it was never the protection. The real protection is rate-limiting + validation + insert-only.

🔐 Admin API → CORS locked down

Only the dashboard's own origin may call it, and it uses cookies. Tight CORS + SameSite cookies means a malicious site's JS can't read your feedback even if it tries — it has no session and the browser won't share the response.

D · Guarding the public slot — rate limits, validation, XSS

  • Rate limiting — cap requests per public key (one noisy tenant can't drown the rest) and per IP (one bot can't flood). Over the limit → 429 Too Many Requests. This is the "noisy-neighbor" containment.
  • Validation — reject anything that isn't a known type, a too-long message, a rating outside 1–5, or a malformed email. Small, strict payloads only.
  • Stored XSS defense — someone will submit <script>…</script> as their message. We store it as plain text and escape it when the dashboard renders it, so it shows up as harmless characters, not running code. (React does this automatically — a reason the stack choice helps here.)

E · Admin API conventions (the "production-grade" stuff)

Endpoints (all under /api/v1):

Method + pathDoes
POST /auth/loginstart a session
GET /feedbacklist · filter · search · paginate
GET /feedback/:idone item + notes
PATCH /feedback/:idstatus / assignee
POST /feedback/:id/notesadd a note
GET /statsdashboard totals
GET /team · /settingsadmin-only

Conventions:

  • Consistent errors: always { error: { code, message } }, with the right HTTP status (400/401/403/404/429).
  • Pagination: ?limit=&offset= + a total count for v1 (note: switch to cursor-based for big datasets).
  • Versioning: the /v1 prefix. Additive changes stay in v1; anything breaking becomes /v2.

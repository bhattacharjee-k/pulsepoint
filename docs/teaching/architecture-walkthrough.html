Three database roles, each with the least power it needs:
• pulsepoint_migrate — owns & changes the tables (used only at setup, never by the running app)
• pulsepoint_ingest — the public path; can only insert feedback
• pulsepoint_app — the dashboard path; can read/update within one tenant

💡 The two paths use separate connection pools. A flood of spam on the public path can only exhaust the ingest pool — the dashboard keeps working. That's the cheap, real version of "separate the read and write paths."

C · End-to-end — what happens when Alice clicks "Submit"

■ write path   ■ read path   ■ attack that fails

  1. Alice is on demo-alpha.html. The page loaded embed.js with data-public-key="pk_alpha_demo".
  2. The widget asks the server for Alpha's config (accent colour, prompt text, which feedback types are on) and renders a small "Feedback" button inside its Shadow DOM bubble — styling can't leak in or out.
  3. Alice clicks it, picks type: bug, types a message, hits submit. The demo page also attaches a stub submitter { externalId: "alpha-1", displayName: "Alice" }.
  4. The widget sends POST /api/v1/public/feedback with header X-Tenant-Key: pk_alpha_demo.
  5. Public API checks the rate limit (per key + per IP), validates the payload, then looks up the key → tenant = Alpha. (Unknown key → rejected.)
  6. It opens a transaction, runs SET LOCAL app.ingest_tenant_id = alpha, and inserts the row. The database itself stamps tenant_id = alpha and refuses any other value. Returns 201 + the new id.
  7. Later, admin@alpha.com logs in → gets a secure session cookie. Opens the dashboard inbox.
  8. Admin API reads the session → finds the membership → tenant = Alpha. Opens a transaction, runs SET LOCAL app.current_tenant_id = alpha, then SELECT … FROM feedback.
  9. RLS quietly appends "…and only rows where tenant_id = alpha". Alice's new row appears. None of Delta's rows do. Admin changes status, adds a note (also tenant-checked).
  10. If admin@delta.com tries to open Alice's feedback by its exact id, their session sets tenant_id = delta, RLS returns zero rows, and they get a 404 — the leak is blocked at the database, even if the app code had a bug.
